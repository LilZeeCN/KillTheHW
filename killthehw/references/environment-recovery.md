# 实验环境恢复

环境损坏并不等于整份作业无法继续。先分清可恢复的软件/配置故障和确实缺少的数据或设备，完成诊断、有限恢复、验证和真实记录。恢复范围由现有任务授权决定，不能因“完成作业”就推导出任意清空集群的权限。

## 先留现场，再选最小恢复路径

1. 记录目标主机/容器、版本、安装路径、配置路径、数据路径、服务启动方式及受影响实验。确认操作的是目标环境，多个节点分开登记。
2. 保存本次相关日志、配置、版本信息、关键目录清单和业务状态；能备份或快照时先保留。不要在诊断前反复重启、覆盖目录或清数据库。
3. 用具体证据提出假设：程序文件缺失、进程引用已删除文件、端口占用、权限错误、依赖/配置不一致、元数据不一致、数据重复等。未知原因写未知。
4. 选择最小变更，说明改变什么和如何回退。普通的可逆恢复在已有授权内继续；涉及额外覆盖或丢弃数据时先展示对象、备份和后果，再只取得缺失授权。
5. 修复后验证进程与服务、再验证业务结果，最后重跑受影响小问；服务能启动不是数据正确的证明。

## 连续作业中的授权衔接

用户明确要求连续推进（如通宵完成多个实验、期间不打扰）时，不要把每个不可逆步骤都停下来等批准，那样整夜会卡死；也不能把"继续做"扩大成任意处置数据的许可。按下述衔接处理：

- **可逆恢复**（重启服务、重装程序、改配置前先备份原件）：直接继续，里程碑记录即可。
- **丢弃失效的实验残留**（元数据已指向不存在的进程、数据已被证实损坏且与本作业无关）：用证据写明"为什么判定失效"，把被删对象先打包保留在任务目录 `evidence/recovery-backup/` 下再删，随后继续；完成后在交付说明中如实披露删了什么、依据是什么、备份在哪。
- **丢弃仍有价值的数据**（作业产出、他人数据、无法重建的内容）：仍必须阻塞并取得授权；连续指令不覆盖这一类。
- 判断属于哪一类拿不准时，按更严格的一类处理，并把它登记为 issue 而不是猜测后继续。

## 常见情形

| 现象 | 先检查 | 恢复与验收重点 |
| --- | --- | --- |
| 安装目录不见，但进程还活着 | 目标 PID、启动命令、进程持有的已删除文件、配置/数据是否独立 | Linux 可对目标 PID 查 /proc 下 exe/cwd 与文件描述符，或使用 lsof。先保留配置和恢复来源，再决定何时停服务；贸然停止可能失去运行现场。 |
| 从另一节点复制程序 | 软件版本、压缩包散列值、CPU/系统、插件依赖、用户权限 | 优先恢复程序目录；节点专属配置、主机名、凭据和数据不能整目录照抄。比对差异，再用最小业务探针验收。 |
| Hadoop/HBase 元数据或 cluster ID 不一致 | 各节点实际配置指向、存储目录、VERSION/元数据、NameNode 与数据节点状态、是否存在既有数据 | 先判断路径错配、节点连错或旧数据问题。保全元数据和数据；不能把删除 VERSION、清 clusterID 或 namenode format 作为通用修复。 |
| 数据导入后行数、平均数不符 | 原始文件、主键、导入次数、目标表/分区、去重规则、查询口径 | 如实记录污染及范围。已授权的更正先备份并核对行级结果；可在隔离的新表验证正确流程，避免覆盖唯一原始数据。 |
| 客户端一直不退出 | PID、提示符、子进程、分页器、连接、实际作业 ID | 用相应客户端批处理/退出机制；先判明当前状态，再决定等待、恢复输入或终止本任务。 |

HDFS 的文件系统状态依赖 NameNode 元数据及日志；程序安装目录恢复与文件系统重新初始化是两件事。涉及既有数据恢复时参考目标版本的 [HDFS 用户指南](https://hadoop.apache.org/docs/r3.3.6/hadoop-project-dist/hadoop-hdfs/HdfsUserGuide.html) 与 [架构说明](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html)，不能只看某个服务是否重新出现。

## 返工记录与报告

每次恢复按里程碑记一条：发现的现象、证据路径、采取的动作、涉及对象、变更前后散列/版本、验证结果和遗留限制。发生什么写什么；没有经历的故障不补写成故事。

报告正文按课程要求选取有用的返工内容，写清“哪个结果受影响、怎样定位、如何恢复、如何确认”。原始错误输出、恢复日志和修正后结果分别保留。服务恢复后仍无法获得的数据或要求的截图，继续作为阻塞，不用成功启动的日志冒充全部作业完成。
